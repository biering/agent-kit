# Scope per submission

Review has tiers. A straightforward review takes about two days. If the build or
metadata touches something sensitive, it can be escalated to a senior specialist
and take up to about two weeks. You cannot predict the tier, but you can avoid
handing the reviewer reasons.

## The first submission is an MVP

- Core action, a free tier that really works, one paywall, onboarding, settings, privacy.
- Nothing "coming soon". If a feature is not ready, it is not in the build.
- One purchase, one price, simple terms.

## What to hold back for later updates

Ship these one at a time, after the app has an approved history:

- Offers shown when someone abandons a purchase.
- Offers on an exit path such as "manage subscription" or "cancel".
- New data collection or a changed privacy answer (change the label in the same version, and say so in the notes).
- Pricing and free-tier changes that touch many screens.
- New categories of user content, health claims, or kid-directed features.
- Large rewrites of onboarding at the same time as anything above.

When you do ship one, explain it in the notes under "Anything unusual" and show
it in the demo video.

## Splitting a big update

If one update mixes a safe change (new screens, bug fixes) with a risky one
(pricing, data, a new offer), consider two submissions, safe one first. Costs:
one more review and an extra release. Benefit: the safe change is not held up by
a slow review of the risky one. Judge by how much you need the safe change out.

## Per-version checklist

- [ ] What changed since the approved version, in one list.
- [ ] Which items on this list are risky, and could they ship separately?
- [ ] Notes updated for this version, including "what is new".
- [ ] Demo video updated for every changed section.
- [ ] App Privacy answers re-checked against what the code now does.
